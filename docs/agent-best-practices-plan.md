# Agent Guard: agent safety practices and implementation plan

**Decision, 4 November 2026.** Keep the authorization engine small and independent of model providers. The next deliverable should be one realistic task running through both OpenAI and Anthropic client-tool loops, with a fake backend that counts actual reads, writes and disclosures. The engine already checks permissions. The largest unanswered question is whether a host integrating a real model consistently puts every protected effect through those checks.

**Implementation update, 4 November 2026.** The local working tree now implements the synthetic effect fixture and both provider adapters from steps 1–2. They share trusted parsing, tenant/resource/version checks, scoped one-time review, backend receipts and bounded result projection. Both runnable commands use offline provider-shaped replay by default and assert backend effects and serialized-request canaries. The test suite covers the same allowed and rejected cases for each provider, including current direct-caller metadata and late completion after cancellation. Installed-package checks also run both examples against packed npm artifacts. The [workflow guide](guides/provider-ticket-workflow.md), [OpenAI adapter](../examples/providers/openai-responses.mjs), [Anthropic adapter](../examples/providers/anthropic-messages.mjs) and [regression tests](../scripts/provider-ticket.test.mjs) document the contract. A live smoke run with a configured provider spend cap remains optional and was not performed. These local changes are not yet published; the historical release audit and counts below remain scoped to the versions they describe.

**Decision-trace update, 4 November 2026.** Step 3 is implemented in the local working tree. The durable executor has opt-in bounded tenant buffers, pseudonymous decision correlation, stable outcome/error codes and an explicit failure-isolated export API. Prepare, review, deny, admit, settlement, cancellation, unknown recovery and reconciliation are covered. Post-admission errors remain distinct from denied effects. Export callbacks never run during admission. The [trace guide](guides/decision-traces.md), [executor tests](../packages/executor/test/traces.test.mjs) and [provider fixture trace tests](../scripts/provider-ticket-traces.test.mjs) describe privacy, retention, tenant scope, retry and crash limitations. This does not change the historical published-version coverage table below.

**Trace validation, 4 November 2026.** `npm run check` passed all 771 tests, including five opt-in Docker cases, with zero skips and the clean-package consumers on Node 26.12.0. All 17 trace/provider-trace cases also passed on Node 22.13.0. Independent review and regressions addressed hostile accessors, export acknowledgment, preparation revision races and the existing reconciliation error contract. Traced admission now reuses its authority snapshot without an extra ledger read. See the [trace guide](guides/decision-traces.md#verification) for benchmark evidence and limits.

**Evaluation implementation, 5 November 2026.** The deterministic portion of step 4 now runs a versioned, original synthetic paired corpus through both provider workflows. It measures completed tasks, exact approved changes, unauthorized backend actions and provider-visible canaries, with guarded/permissive/deny-all controls. Its full gate requires every case/provider/control row and detects broken positive controls, missing data and a deny-all substitution. The [evaluation guide](guides/provider-outcome-evaluation.md), [corpus](../evals/provider-tools/corpus.json) and [grader tests](../scripts/provider-evaluation.test.mjs) document reproduction and limitations. Public reserved families are not a blind holdout; live-model repeated trials, independently reserved data and production utility calibration remain open parts of step 4.

**Step 4 model-selected trials.** The OpenAI and Anthropic evaluators run paired benign and adversarial tickets. For release decisions, a version 3 private configuration enrolls minimum benign, adversarial and same-repeat paired task-success rates before dispatch. The evaluator checks each case pair and the full run against those rates and requires complete safety evidence. Representative measurements still need independently curated cases, thresholds justified against a baseline, an enrolled model and an authorized budget. [Operator guide](guides/model-selected-provider-trials.md) · [Evaluation runner](../scripts/evaluate-provider-trials.mjs)

**Joined isolation implementation, 5 November 2026.** The local acceptance portion of step 5 now runs a disposable, pinned-Node MCP peer inside the existing fixed Docker isolation profile, joined to the managed connection and durable executor. It tests actual approved/forbidden dispatch, host credential custody, egress restrictions, metadata drift, renewed review, reconnect, cancellation, unknown-outcome reconciliation and cleanup. A second real loopback HTTP profile verifies credential fingerprint/issuer/audience/subject/scope/expiry binding with synthetic signed proofs, redirect rejection and private-destination denial. The [acceptance guide](guides/mcp-isolation-acceptance.md) describes the 21-check report and native-platform gate. Real company IdP/TLS/JWKS refresh, blind live-model evaluation and untested native host profiles remain open evidence requirements; the fixture does not claim to complete those deployment checks.

**Joined isolation validation, 5 November 2026.** `npm run check` passed all 787 tests with zero skips, including the six real Docker runtime tests, and installed-package consumers on Node 26.12.0. The macOS platform gate separately passed all 16 selected tests. All nine MCP/platform-verifier tests passed on Node 22.13.0. The [recorded 21-check report](validation/mcp-isolation-2026-11-05.json) binds evaluator/fixture hashes and records completed cleanup, one approved write, one approved remote call, seven rejected invalid authorization proofs and zero redirect leaks. This is macOS arm64 with a Linux Docker VM evidence; no untested host receives certification from it.

**Verified remote credentials, 5 November 2026.** The next local portion of step 5 now binds a pre-issued JWT access token to an owned HTTPS MCP session using maintained JOSE signature verification and an exact host-enrolled issuer/JWKS/resource/subject/scope policy. Replacement invalidates the old session before fetching fresh keys and requires renewed approvals; expiry and terminal revocation reject further dispatch. Scoped additional CA trust and actual socket-lookup DNS regressions exercise TLS, mixed/private addresses, rebinding answers and late resolution. The [credential guide](guides/verified-mcp-credentials.md) describes the restricted access-token profile, nine real-HTTPS/lifecycle regressions, conservative UNKNOWN reconciliation and the distinction between explicit JWKS replacement and issuer revocation. Company token acquisition/refresh, production IdP/TLS, live DNS infrastructure, browser rollout and untested native hosts remain separate evidence requirements.

**Verified credential validation, 5 November 2026.** The full `npm run check` passed all 800 tests, zero skips and clean installed-package consumers on Node 26.12.0. The macOS platform gate passed all 33 selected tests, and 22 credential/network/platform-verifier tests passed on Node 22.13.0. The installed consumer independently signs access tokens and verifies protected HTTPS effects against packed packages. [Recorded local evidence and source hashes](validation/verified-mcp-credentials-2026-11-05.json) · [Credential profile and remaining integration work](guides/verified-mcp-credentials.md).

**Step 6 build artifact admission.** A host can now enroll exact component bytes, tenant/path, producer signing key, build type and reported source dependency in an `ArtifactBroker` policy. The broker checks signed DSSE/in-toto/SLSA evidence at import, issues policy-bound receipts and rejects unreceipted sandbox inputs. The [deployment guide](guides/build-artifact-admission.md) describes rotation, the restricted attestation format and the real Docker import/derivation test. This implements the external-file admission portion of the company pilot. Live tenant enrollment, identity/cloud evidence, representative load, recovery and independent promotion review remain open.

**Step 6 independent pilot review.** The executor now verifies a bounded company-pilot dossier for one tenant, candidate, identity provider, HTTPS origin, tool and read-only AWS metadata target. It checks the actual candidate's build signature, separately signed observations, source report digests and an independently enrolled reviewer signature. It enforces the enrolled time window and recomputes the operational gates before emitting a redacted receipt. The CLI explicitly distinguishes rehearsal from company evidence. Enrolling the company's real roles, running the approved pilot and obtaining its independent sign-off remain deployment work. [Operator guide](guides/pilot-review.md)

## What the research changes

- **Enforce at the point of effect.** Both providers give host code a place to execute client-defined tools. A narrow schema helps the model express a request. An independently authenticated host still resolves its authority. Anthropic's security research on data and control flow supports retaining provenance through tools and explicit capability checks. The current SDK's labels and grants implement a narrower mechanism than the CaMeL architecture. [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling) · [Anthropic client tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls) · [CaMeL paper](https://arxiv.org/abs/2503.18813)
- **Put approvals where the effect occurs and mark the input's origin.** OpenAI's Agent Builder guidance recommends review of MCP operations, including reads, and structured data across workflow boundaries. Anthropic directs hosts to return external data in designated tool-result blocks. Offer a strict per-call review profile for external MCP operations. Document any host-approved lower-friction policy for bounded reads and measure its risk and completion rate. Tool-description approval, per-effect approval and authenticating a reviewer are different decisions. [OpenAI agent safety](https://developers.openai.com/api/docs/guides/agent-builder-safety) · [Anthropic result handling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls) · [MCP security guidance](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)
- **Judge effects and useful work together.** AgentDojo pairs ordinary tool tasks with hostile content and measures what happens in the environment. Provider guidance recommends task-specific data, repeated trials, outcome grading and human calibration. A bot that refuses every ticket gets a poor legitimate-completion score. A model that apologizes after a forbidden write still fails the safety test. [AgentDojo paper](https://arxiv.org/abs/2406.13352) · [Anthropic agent evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) · [OpenAI evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
- **Reduce integration complexity.** Use one client-tool loop per provider, clear tool names, limited result fields and an explicit stop condition. Introduce additional agents or an SDK-specific hook only when measured outcomes justify its cost. Provider-built-in tools execute in a different trust boundary. A host must disable them in a protected profile or document and independently control that path. [Anthropic workflows](https://www.anthropic.com/research/building-effective-agents) · [Anthropic tool design](https://www.anthropic.com/research/writing-tools-for-agents) · [OpenAI building-agents learning track](https://developers.openai.com/tracks/building-agents)

## Implementation sequence

Targets below are proposals for this project. New paths are named in code formatting. Start with two maintainers' questions on every example: *Which component can actually perform the effect? Where is the evidence that a rejected request did nothing?*

1. **P0 · Prove the installation and the first protected effect.** SDK maintainer. Reuse the published macOS launcher workaround from the release notes wherever the alpha.2 CLI is recommended. Run the installed npm shims on the next candidate and verify them from the registry after publication. Build one synthetic ticket store with a read of ticket 123, a write requiring human approval, an out-of-tenant ticket 456 and a private canary. Keep a counter for each effect. **Exit:** the two installed commands produce usage, the approved write occurs once, and denied, replayed or altered calls leave the store unchanged. The existing CLI source fix is a starting point. [Package checks](../scripts/check-packages.mjs) · [CLI guards](../packages/agent-map/src/cli.ts) · [Existing synthetic example](../examples/basic.mjs)

2. **P0 · Route two real provider protocols through that fixture.** SDK/integration maintainer, after step 1. Add `examples/providers/openai-responses.mjs` and `examples/providers/anthropic-messages.mjs`. Give the model only the tools available for this task, with strict schemas where supported. Use host-issued task and tenant identity and the same trusted parser/resolver in both examples. For OpenAI, collect each completed function call, parse its arguments and return a `function_call_output` bound to its `call_id`. For Anthropic, handle each `tool_use` block and return `tool_result` with the matching `tool_use_id`. Treat provider IDs as conversation correlation. Keep the host's prepared action, approval digest and backend idempotency identity separate. Route through prepare → review if required → execute → bounded result. Keep external text in the tool-result channel. Scope provider credentials to the trusted host. Begin with client-defined tools only and list every disabled server-side or raw transport capability. **Exit:** replay captured synthetic protocol messages offline for both providers with no keys. Cover parallel calls, duplicate/mismatched IDs, partial streamed arguments, abort, timeout, denial, expired approval, malicious result text, maximum turns and budget exhaustion. Assert no forbidden effect and exactly one authorized effect. Permit an optional live smoke run with explicit credentials, one synthetic tenant, hard spend/turn caps and the same fake backend. [OpenAI calling contract](https://developers.openai.com/api/docs/guides/function-calling) · [Claude tool handling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls) · [Existing public definitions](../packages/executor/src/adapters.ts)

3. **P1 · Make a decision diagnosable without exposing its payload.** Executor maintainer and security reviewer, after step 2 defines the events. Add an opt-in bounded event sink alongside the existing audit. Use a scoped correlation ID, outcome, stable rule/error code, revision and latency for prepare/deny/review/admit/settle/unknown. Document field limits, retention, access and dropped-event counting. Default to omitting raw prompt, argument, result, credential and customer identifiers. Test a full sink, failed exporter, retries, parallel approvals and cross-tenant reads. **Exit:** reconstruct each fixture's decision and final state from sanitized events. Canary scans of the exported test data return zero matches. A failed optional exporter never authorizes or redispatches an action. Re-run the existing admission benchmark to catch observer overhead. [Current audit](../packages/executor/src/executor.ts) · [Benchmark](../scripts/benchmark-admission.mjs) · [OpenAI workflow evaluation](https://developers.openai.com/api/docs/guides/agent-evals)

4. **P1 · Turn attacks and legitimate tasks into a release gate.** Evaluation owner, using steps 2–3. Keep the 12 deterministic scenario pairs and add a proposed `evals/provider-tools/` corpus with immutable setup, data provenance, permitted outcome, forbidden sinks and a known-good solution. Seed with reviewed, sanitized incidents and locally adapted AgentDojo-style tasks. Reserve held-out task families and attack variants before tuning. Check corpus licenses before copying fixtures. Compare a deliberately permissive sandbox control, guarded run and deny-all control. Grade backend state and canary exfiltration separately from requested calls, explicit denials and user-visible completion. **Exit:** each runnable fixture has both a benign and an attack case, a deterministic checker and a resettable environment. Initial proposed gate is zero forbidden effects in the deterministic suite and complete benign reference solutions. For stochastic model runs record model/configuration, sample count, repeated-trial consistency, attack successes, legitimate completion, unnecessary approvals, cost and p95 latency. Report denominators and uncertainty. Calibrate a benign completion target and regression tolerance on a baseline before enforcing a percentage. Keep paid trials opt-in with a fixed budget. [Scenario cases](../packages/scenarios/src/catalog.ts) · [AgentDojo](https://arxiv.org/abs/2406.13352) · [Evaluation methods](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

5. **P1 · Prove transport, process and data isolation as one deployment.** Runtime/security maintainer, after the provider recipe can produce a full trace. Exercise a disposable untrusted MCP server with reviewed launch options and no raw host credentials, shell, Docker socket or alternate egress route. For the remote profile, bind the negotiated endpoint, verified issuer/audience/subject/scopes and network policy through refresh/reconnect. Use the existing credential library boundary and restricted network adapter. Run both permitted and forbidden local-process/network cases, stale approval after reconnect, cross-origin redirect, private-IP/DNS-rebinding attempts and explicit per-call review. Test hostile tool results attempting to change recipient or policy. Extend the existing native matrix to retain unskipped results, image digest, ACL evidence on Windows, VM restart/recovery and kill/rollback procedures. **Exit:** no secret reaches an unapproved sink, new admission after revocation is denied, already-dispatched work is cancelled or reconciled, and a benign allowed task succeeds on each supported host. Declare an untested host unsupported for the protected profile. 6. **P2 · Make a company pilot the promotion decision.** Deployment owner and an independent reviewer, after steps 1–5. Run one enrolled tenant with its IdP, TLS, read-only AWS role, representative task load and recovery backup. Verify denied tenant reads, revocation, restore, TLS/key rotation, incident reconciliation and the documented latency budget. Map each claimed external component to a verified build identity, digest and trusted builder under an explicit admission policy. Retain the pilot report and outstanding exceptions. **Exit:** an independent reviewer signs the narrowed boundary, or the affected deployment claim stays open. Treat distributed workers as a separate design only when a customer requires them. They need shared atomic reservations, fencing and partition tests.
