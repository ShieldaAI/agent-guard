# Agent Guard 0.1.0-alpha.2

Release preparation date: 1 November 2026. This source release is prepared for
publication under the npm `alpha` tag. Registry publication, package integrity
and the final release commit have not yet been verified for this version.

The release adds a durable executor and a company-scoped inventory reference
service to the existing Agent Guard packages. It also extends managed MCP
authorization, argument validation and conformance coverage. All packages remain
experimental.

## Packages

| Package | Changes in this alpha | Minimum Node.js |
| --- | --- | --- |
| `@shieldaai/agent-guard` | Typed argument normalization and resource-version binding for scoped execution. | 22 |
| `@shieldaai/agent-guard-mcp` | Managed connections, session-bound metadata approval, restricted HTTP transport and lifecycle inventory. | 22 |

The five packages use exact matching internal versions. After publication is
verified, install only the packages needed by the host application, pinned to
`0.1.0-alpha.2` or selected explicitly with `@alpha`. Preserve existing `latest`
tags for core, MCP and scenarios. The first executor and Agent Map publications
require their assigned tags to be checked separately; a `latest` tag does not
make an alpha production-ready.

The private React/Cytoscape viewer is built from the repository. The Python
Cartography integration remains a separately versioned source package. This npm
release publishes neither component and creates no company-hosted service.

## Inventory and operational changes

The trusted host can export tenant-scoped snapshots with persistent inventory
identity, a validated host manifest and observed MCP lifecycle state. The
Cartography collector stages complete projections before publication, joins
exact AWS references, retains independent freshness and unresolved coverage,
and preserves source-generation retirement through backup and reconstruction.
The reference service exposes company/team-scoped graphs, changes, explanations
and bounded IAM policy candidates. Inventory never grants execution authority
and remains outside the executor admission path.

The final implementation audits corrected duplicate graph relationships hiding
missing edges, private report-file replacement races, and a separate pilot
configuration-file race. Follow-up hosted checks corrected Node 22 diagnostic
test assumptions and Windows path/fixture cleanup behavior. The
[changelog](../../CHANGELOG.md) contains the complete change list.

## Verification and publication gates

The versioned source passed a clean `npm ci --ignore-scripts` installation and
`npm run check` on macOS arm64 / Node 26.12.0: **719 tests passed, zero failures
or skips**, with the pinned Docker sandbox image enabled. Packed declarations,
README examples, executor/MCP/reference consumers and the installed identity
HTTPS consumer passed. `npm run pack` produced all five alpha.2 tarballs.

The implementation baseline in [PR #4](https://github.com/ShieldaAI/agent-guard/pull/4)
passed all eleven checks on commit `566628730a11ddfd972884a9cae1daa8da24b88e`.
Those checks included Linux Node 22/24/26, macOS 24, Windows 24, CodeQL,
dependency review, the Python/Neo4j integration and the recovery pilot. Hosted
Node jobs skipped Docker isolation cases without a configured image; Windows
also skipped one POSIX-only case. These results do not certify native isolation.

The [local publication/report review](../../deployment/cartography/validation/publication-report-review-2026-10-31.md)
preserves the earlier full local suites, reconstruction checks and 100-source
capacity benchmark. The hosted pilot uses the smoke benchmark profile. These
reports describe their recorded revisions and environments, not registry
verification of this release version.

Before publication, the versioned release must pass its own local checks,
package-content inspection, final pull-request checks and merged-commit CI and
CodeQL checks. After publication, verify all five exact versions, tarball
integrities and `gitHead` values, then run clean registry consumers and record the
assigned dist-tags. The [release procedure](../releasing.md) specifies the order.

## Deployment boundaries

The executor has one authority owner and does not provide distributed
enforcement. The core remains an in-process guard rather than an OS sandbox.
Inventory and cloud policy candidates are reference evidence, with unknown
effective-permission assessments where provider context is incomplete.

The local pilot uses a POSIX host profile; native Windows pilot launch is
explicitly unsupported, with WSL2 documented as the supported route. The full
native Linux/macOS/Windows Docker/VM isolation matrix and independent security
review remain separate protected-deployment gates. Ordinary hosted tests and
packaged consumers do not replace them.

Company AWS enrollment, provider-neutral OIDC client enrollment, trusted TLS,
exact subject bindings, representative deployed workloads and independent
rollout review remain deployment work. The documented 9/10 assessment is a local
acceptance checklist, not a production certification. See the
[deployment profile](../../deployment/README.md) and
[Cartography runbook](../../deployment/cartography/RUNBOOK.md).
