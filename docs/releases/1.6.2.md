# Agent Guard 1.6.2

The Agent Guard Check GitHub Action now works in a merge queue. The other packages have no changes;
all seven move to 1.6.2 together, as every release does.

## Why

A reader asked what happens when two pull requests are each fine alone but not together: one adds
a database MCP server, the other adds `WebFetch`, and the first merges after the second's last
check ran. The pull-request check on the second is then stale. Without a merge queue, "Require
branches to be up to date" covers this. With one, the queue's own run is what should catch it, but
the Action did not handle that run well.

## What changed

### `@shieldaai/agent-guard-check` GitHub Action

- **Base commit in a merge queue.** On `merge_group` runs the Action took the base only from the
  pull-request event, so it found none. It then reported every finding in the queued commit, and a
  required check could hold up pull requests that changed no agent configuration. It now compares
  with `github.event.merge_group.base_sha`, so the queue run reports what the queued change adds,
  the same as on the pull request.
- **Code-owner rules for the queue's branch.** AGC-GOV-004 reads branch rules for the queue's
  target branch. The queue names it as a full ref (`refs/heads/main`), which the Action shortens.
- **README workflow.** The example lists `merge_group` next to `pull_request`, with a note on when
  the trigger is needed.

## Upgrading

If your repository uses a merge queue and the check is required, add `merge_group` to the
workflow's `on:` and move the Action pin to the 1.6.2 commit. Workflows that set `base:` by hand
keep working. Without a merge queue there is nothing to change.

## Known limits

- The merge-queue run has not yet been tried in a real GitHub merge queue; the tests cover the
  Action's defaults and branch-name handling.
- The pull-request comment (`comment: true`) is not posted from a merge-queue run.
- `@shieldaai/agent-map` stays experimental and outside the 1.x compatibility promise.
